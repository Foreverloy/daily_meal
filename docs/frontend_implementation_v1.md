# Daily Meal 前端 V1 实现文档

## 1. 目标与范围

前端由 AI 实现，用户主要专注 Go 与 Agent 开发。先交付支持电脑和手机浏览器的网页应用，后续通过 Capacitor 复用网页代码制作 iOS App。

前端 V1 对接[后端 V1](implementation_v1.md)，完成今日饮食、食物库、菜品库和目标设置四个模块。参考“薄荷健康”相关操作流程，并采用本项目已确认的简化规则。

开发顺序为 Go 后端 V1 → Vue 网页 V1 → 后续 Agent 与 iOS 接入。聊天、截图识别、菜单推荐和原生 App 构建不属于网页 V1 的交付范围。

## 2. 技术栈

| 部分 | 选型 | 用途 |
| --- | --- | --- |
| UI 框架 | Vue 3 | 单文件组件，统一使用 Composition API 和 `<script setup lang="ts">` |
| 语言 | TypeScript | 请求、响应、表单和页面状态类型 |
| 构建 | Vite | 开发服务器、接口代理和生产构建 |
| 路由 | Vue Router | 页面导航、详情页和日期查询参数 |
| 样式 | HTML + CSS | 响应式布局、统一颜色与间距、复用表单和卡片 |
| 接口调用 | Fetch API | 在统一请求模块中处理 JSON、HTTP 状态和后端错误 |
| 状态 | Vue `ref` / `reactive` / composables | 页面数据、表单状态和请求状态 |
| 验证 | `vue-tsc`、Vitest、Vue Test Utils、Playwright | 类型检查、关键组件测试、浏览器流程验证 |
| iOS 后续路线 | Capacitor | 将 Web 构建产物集成到 iOS 应用并接入设备能力 |

使用 Vue 官方 `create-vue` 初始化项目，启用 TypeScript、Vue Router 和测试工具，提交依赖锁文件。官方脚手架基于 Vite，默认示例采用 Composition API；版本在实际初始化时选择相互兼容的稳定版本并锁定。[Vue 官方快速开始](https://vuejs.org/guide/quick-start.html)

V1 使用少量自有基础组件和局部状态，不额外引入全局状态库、请求缓存库或大型 UI 体系。确有共享状态或复杂组件需求时，再集中选择依赖。

## 3. 页面与交互

主导航包含“今日”“食物”“菜品”“目标”。手机采用便于触达的底部导航，电脑采用顶部或侧边导航；两者复用页面和组件。

| 页面 | 建议路由 | 主要内容 |
| --- | --- | --- |
| 今日饮食 | `/?date=YYYY-MM-DD` | 日期切换、营养进度、三餐记录、添加与纠正记录 |
| 食物库 | `/foods` | 名称搜索、分页、进入详情或新建 |
| 食物表单与详情 | `/foods/new`、`/foods/:id`、`/foods/:id/edit` | 营养基准、名称、各项营养数据 |
| 菜品库 | `/recipes` | 名称搜索、分页、进入详情或新建 |
| 菜品表单与详情 | `/recipes/new`、`/recipes/:id`、`/recipes/:id/edit` | 名称、食材与用量、后端返回的营养合计 |
| 目标设置 | `/goals?date=YYYY-MM-DD` | 默认目标、指定日期覆盖、恢复默认 |
| 饮食记录表单 | `/records/new`、`/records/:id/edit` | 日期、餐次、食物或菜品选择及修改 |

### 3.1 今日饮食

- 默认打开业务时区的今天，允许选择其他日期。日期使用字符串保存，避免通过 UTC 时间转换导致日期偏移。
- 展示热量与三大营养素的目标、已摄入、剩余额度；钠、维生素等只显示摄入。
- 分为早餐、午餐、晚餐，每餐显示明细与合计，并提供添加记录入口。
- 添加时带入当前日期和餐次，用户选择“食物”或“菜品”。
- 食物填写数量及允许的单位；菜品选择后直接记录整道，不出现份数、食用比例或成品重量输入。
- 同一餐可逐条添加食物和菜品，保存成功后刷新该日期的记录与营养汇总。
- 编辑记录可调整日期、餐次和内容；删除后刷新汇总。改动记录日期时，同时更新原日期与新日期的展示数据。

### 3.2 食物维护

- 创建时填写名称、基准单位 `g` / `ml` 和每 100g/ml 的营养数据；编辑时基准单位只读。
- 热量必填；其他已支持营养指标可为空。输入框旁固定展示营养单位，例如蛋白质 g、钠 mg。
- 空白营养值表示未知，数字 0 表示已知为零，不将空字符串自动转为 0。
- PATCH 只提交实际修改的字段；明确清空可选营养值时提交 `null`，保留其他字段。
- 食物用量只提供 g/kg 或 ml/L 中与其基准匹配的选项。
- 搜索结果展示名称和计量基准，选择及提交使用食物 ID。

### 3.3 菜品维护

- 输入菜名，通过食物搜索添加食材，并填写每种食材的数量和单位。
- 可以移除或调整食材，至少保留一种；同一种食材在表单中合并为一行。
- 保存时提交完整配方，营养合计以 Go 返回值为准。编辑阶段只维护食材与用量，不另写一套营养汇总算法。
- 详情显示固定配方和整道菜营养，并可带入饮食记录表单。
- 修改模板影响新记录；历史饮食详情展示记录快照，不能用当前食物或菜品详情替换。

### 3.4 目标设置

- 输入每日大卡及蛋白质、碳水、脂肪的供能百分比，显示比例合计，提交前校验合计为 100%。
- 清楚区分“修改默认目标（从今天生效）”与“仅修改所选日期”。
- 展示当前目标来源：默认、该日覆盖、未设置；删除日期覆盖的操作显示为“恢复该日默认目标”。
- 目标不存在时引导设置，仍允许查看和记录饮食。
- 克数目标和目标对比读取 Go 返回结果。

## 4. 接口与展示约定

API 前缀统一为 `/api/v1`，详细请求和响应以 Go OpenAPI 为准。TypeScript 类型集中维护，接口变更时同步更新，页面不自行猜测字段。

| 前端操作 | 后端接口 |
| --- | --- |
| 获取每日汇总 | `GET /daily-summary?date=...` |
| 查询当天记录 | `GET /meal-entries?date=...`，可附带 `meal_type` |
| 新增、查询、修改、删除记录 | `POST /meal-entries`；`GET/PATCH/DELETE /meal-entries/{id}` |
| 食物搜索、创建和维护 | `GET/POST /foods`；`GET/PATCH /foods/{id}` |
| 菜品搜索、创建和维护 | `GET/POST /recipes`；`GET/PUT /recipes/{id}` |
| 默认目标 | `GET/PUT /goal-settings/default` |
| 日期目标 | `GET/PUT/DELETE /daily-goals/{date}` |

- 统一请求模块区分网络错误、非成功 HTTP 状态和业务字段错误；`204` 响应不解析 JSON。
- `422` 的 `error.fields` 显示在对应输入项旁；其他错误用简短提示展示，并保留未保存的表单内容。
- 提交期间禁用重复提交，成功后显示结果。写入请求发生网络中断时，不自动重发；提示用户先刷新确认是否已保存。
- 首次加载、空列表、失败、提交中分别展示明确状态，不把尚未加载的数据展示为零。
- 已知零值显示 `0`；全部未知显示“未知”；`complete=false` 且存在 `known_total` 时显示“已知合计，数据不完整”。
- `remaining=null` 显示“暂无法计算”，不展示达标判断；负值显示“超出”，不截断为零。
- 汇总中的历史记录名称和营养使用快照；数值精度和营养单位按接口统一格式化。
- 默认业务时区为 `Asia/Shanghai`，与 Go 配置保持一致；切换日期或快速搜索时取消或忽略旧请求，避免旧结果覆盖新页面。
- 饮食记录修改后重新读取服务端结果，Go 是记录、营养汇总和目标计算的唯一事实来源。

## 5. 代码组织与部署

前端放在同一仓库的 `frontend/`，独立管理依赖和构建产物。建议结构：

```text
frontend/
  src/
    api/          # 请求封装、接口函数、请求与响应类型
    components/   # 导航、表单、营养展示、记录列表等共享组件
    composables/  # 页面间确有复用的请求和交互逻辑
    views/        # 今日、食物、菜品、目标和记录页面
    router/       # 路由定义
    styles/       # 主题变量、布局与基础样式
  tests/          # 关键组件测试与浏览器流程测试
```

- 手机单列展示，宽屏增加内容宽度或分栏；按钮、表单、弹层同时支持触摸与键盘操作。
- 原生表单元素提供标签，错误提示可定位到字段；弹层管理焦点，手机键盘打开后仍能完成输入和保存。
- 开发时使用 Vite 代理 `/api` 到 Go 服务，Go 与 PostgreSQL 沿用后端 Docker Compose。
- 生产构建输出静态文件，由静态服务器托管；Web 优先同域访问 Go API，并正确处理页面路由刷新。
- 请求基地址集中配置。Web 可使用相对地址；iOS 阶段改为可访问的 HTTPS API 地址，不依赖开发机的 localhost。
- 前端配置仅包含可公开的配置项，模型密钥和数据库凭据由后端管理。

## 6. 开发顺序与验收

1. **搭建基础工程**：Vue、TypeScript、路由、基础样式、请求模块和四个主导航。
2. **目标与食物**：完成设置、搜索和编辑，验证空值、单位与表单错误。
3. **菜品**：完成食材选择、配方保存、详情及后端营养合计展示。
4. **饮食与汇总**：完成混合记录、日期切换、编辑删除和刷新。
5. **响应式与联调**：在电脑和手机浏览器验证完整流程，执行类型检查、构建和关键测试。

验收重点：

- 通过网页跑通“设置目标 → 创建食物 → 创建菜品 → 记录三餐 → 查看汇总”。
- 一餐可以同时记录食物和菜品；菜品默认整道吃完。
- 未知、零和部分已知正确区分，历史快照与后端一致。
- 编辑、删除、补记和目标覆盖立即反映到正确日期。
- 接口失败时保留输入，不显示虚假的保存成功；提交操作不因重复点击重复触发。
- 手机没有页面级横向溢出，输入和保存按钮可用；电脑布局清晰；路由刷新能打开对应页面。
- Vitest 与 Vue Test Utils 覆盖关键输入和展示边界；Playwright 覆盖主要业务流程及失败场景。测试使用隔离数据，不改动个人真实饮食记录。

## 7. 后续 Agent 与 iOS

### Agent

新增聊天页面和截图上传入口，通过 Go 调用 Python Agent。前端负责展示回答、补充提问、推荐卡片和执行结果，后端负责工具执行与数据写入。

流式交互采用约定的 SSE 事件，区分文本片段、需要补充信息、操作结果、完成和失败。HTTP 数据块不等于完整事件，客户端按事件边界解析。事件结构在 Agent 阶段另行确定。

记录或目标修改成功后，重新读取相关业务数据；推荐卡片不自动当作饮食记录。断线或结果不明确时先查询操作状态，避免重复写入。

### iOS

使用 Capacitor 将 Vue Web 构建产物集成到 iOS 应用中，复用页面、接口和业务交互；Capacitor 提供原生容器及设备能力插件接入。[Capacitor 官方文档](https://capacitorjs.com/docs)

iOS 阶段单独完成安全区域、键盘、导航、相册选择、权限、HTTPS API 连接与流式响应验证，并进行真机测试、签名和发布。网页复用不等于免除平台适配；本阶段不引入另一套 React Native 前端。
