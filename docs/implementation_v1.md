# Daily Meal 后端 V1 实现文档

## 1. 目标与范围

通过个人饮食管理项目练习 Go 后端开发，参考“薄荷健康”的相关使用流程。V1 交付可独立使用的 Go HTTP API，后续前端与 Python Agent 复用同一套业务能力。

V1 包含：

1. 默认营养目标与指定日期的目标设置。
2. 食物创建、查询、修改及营养数据维护。
3. 固定菜品配方管理和营养计算。
4. 早、中、晚餐的混合饮食记录，支持补记、修改和删除。
5. 每餐、全天营养汇总及目标对比。

后端 V1 按个人使用设计，不引入多用户体系。Python 服务、截图识别、对话、菜单推荐和任务队列属于后续阶段。前端采用 Vue 3 + TypeScript + Vite，页面实现与后续 iOS 接入见独立的[前端 V1 实现文档](frontend_implementation_v1.md)。

## 2. 技术与职责

| 部分 | 选型与职责 |
| --- | --- |
| HTTP 服务 | Go + Gin：请求解析、参数校验、错误响应 |
| 业务逻辑 | 普通 Go Service：目标解析、单位换算、营养计算、记录保存 |
| 数据访问 | GORM + PostgreSQL：查询、约束和事务 |
| 数据库迁移 | Goose：版本化 SQL 迁移 |
| 接口文档 | OpenAPI：请求、响应、单位、空值和错误约定 |
| 开发环境 | Docker Compose：Go 服务和 PostgreSQL |
| 验证 | Go testing/httptest、PostgreSQL 集成测试、CI |

调用关系为 `HTTP Handler → Service → 数据访问`。营养计算和单位换算作为独立 Go 函数，供菜品、记录及未来 Agent 工具共同使用。

## 3. 业务规则

### 3.1 每日目标

- 输入每日热量 `energy_kcal`，以及蛋白质、碳水、脂肪的供能百分比。
- 热量必须大于 0；各百分比在 0～100 之间，合计为 100。
- 克数由后端推导，不作为另一套独立目标保存：

```text
蛋白质目标 g = 每日大卡 × 蛋白质百分比 ÷ 100 ÷ 4
碳水目标 g   = 每日大卡 × 碳水百分比 ÷ 100 ÷ 4
脂肪目标 g   = 每日大卡 × 脂肪百分比 ÷ 100 ÷ 9
```

- 默认设置按日沿用；修改默认设置从当天生效，保留之前日期适用的版本。
- 指定日期可设置覆盖值；删除覆盖值后，恢复该日期适用的默认目标。
- 每餐只记录摄入，不设置独立餐次额度。钠、维生素等不设置目标。
- 首次设置默认目标之前的日期，没有目标时返回 `null`，不套用之后的设置；允许单独补设该日目标。
- 业务日期使用 `YYYY-MM-DD`。V1 业务时区默认 `Asia/Shanghai`，统一用于判断“今天”。

### 3.2 食物与单位

| 计量类型 | 输入单位 | 内部单位 | 营养基准 |
| --- | --- | --- | --- |
| 重量 | `g`、`kg` | `g` | 每 100g |
| 体积 | `ml`、`L` | `ml` | 每 100ml |

- 每种食物选择一种基准单位 `basis_unit`，创建后固定。名称和营养数据可修改。
- `1kg = 1000g`，`1L = 1000ml`；数量必须大于 0，不跨重量、体积换算。
- 不支持个、份、碗等食物用量单位。鸡蛋按 g，牛奶可以按 ml。
- 食物应有可辨别的名称，例如生米、熟米饭、某品牌牛奶，选择时使用食物 ID。
- 营养数据统一保存在 `nutrition_per_100` 中，热量必填，其他营养指标可为空，已知数值不得为负。
- 固定字段包括 `energy_kcal`、`protein_g`、`carbohydrate_g`、`fat_g`；可选字段包括 `sodium_mg`、`calcium_mg`、`vitamin_c_mg`、`vitamin_d_ug` 等，按实际数据逐步扩展。
- 营养字段及单位由代码统一定义。食物的用量单位不改变营养素单位，例如牛奶用 ml、蛋白质用 g、钠用 mg。
- 食物热量保存录入值，不强制使用三大营养素反推并覆盖。

```text
摄入营养 = 每 100g/ml 的营养 × 换算后的摄入量 ÷ 100
```

V1 通过接口维护结构化数据。以后导入截图或公共数据时，先转换为同一基准，再调用食物接口；例如“每 250ml”的营养转换为“每 100ml”。

### 3.3 菜品

- 菜品由名称、食物 ID 和每种食物的用量组成，至少有一种食材。
- 食材数量使用对应食物允许的单位，保存时统一换算为 g 或 ml。
- 菜品热量和其他营养按全部食材求和；不同食材的重量与体积无需相加。
- 默认一道菜全部吃完，记录时直接计入整道菜的营养，不设置份数、摄入比例或成品重量。
- 修改模板会影响之后的菜品查询和新记录，已保存的饮食记录保持原快照。
- 菜品营养由当前食材数据计算，避免单独维护一份可能过期的模板营养总量。

示例：番茄炒蛋包含鸡蛋 400g、番茄 100g、番茄膏 50g、蒜 10g。记录这道菜时，计入这些食材的全部营养。

### 3.4 饮食记录与快照

- 餐次固定为 `breakfast`、`lunch`、`dinner`；同一天同一餐允许多条记录。
- 一条记录引用一种食物或一种菜品；同一餐可混合两类记录。
- 食物记录填写数量和单位；菜品记录只需选择菜品，表示整道吃完。
- 日期可指定，未指定时使用当天。支持查询、补记、修改和删除。
- 食物快照保存当时名称、基准单位和每 100g/ml 营养；菜品快照保存当时名称、食材组成、用量及食材营养。
- 记录保存当次营养计算结果。以后修改食物或菜品，不重新计算历史记录。
- 仅修改日期或餐次时，营养快照不变；修改食物摄入量时，使用该记录原有的每 100g/ml 营养重新计算。
- 更换所引用的食物或菜品时，重新获取所选内容的快照。删除或修改记录后，汇总立即反映变化。

### 3.5 缺失数据与汇总

- `0` 表示已知为零，`null` 或未提供表示未知。
- 每个营养指标独立汇总，返回 `known_total`（已知部分合计）与 `complete`（数据是否完整）。
- 有摄入但该指标全部未知时，`known_total` 为 `null`；部分已知时返回已知部分的合计，`complete` 为 `false`。
- 没有饮食记录时，摄入合计为 0，`complete` 为 `true`。
- 默认统计代码已支持的营养指标，包括全部缺失的指标，避免将其静默隐藏。
- 热量和三大营养素返回目标、摄入和剩余额度；只有目标存在且摄入完整时才计算剩余额度，否则返回 `null`。
- 剩余额度可以为负，表示超出目标。其他营养素只返回摄入与完整性。
- 数量和营养计算保留中间精度，展示时再格式化；不逐项提前取整。

## 4. 数据模型

使用以下 6 张业务表。表均包含主键及创建、更新时间；日期字段使用 PostgreSQL `DATE`，数量及目标数值使用 `NUMERIC`，营养对象和快照使用 `JSONB`。

| 表 | 核心字段 | 用途 |
| --- | --- | --- |
| `goal_settings` | `effective_on`、`energy_kcal`、三个供能百分比 | 默认目标的生效记录，`effective_on` 唯一 |
| `daily_goals` | `date`、`energy_kcal`、三个供能百分比 | 某日的完整覆盖目标，`date` 唯一 |
| `foods` | `name`、`basis_unit`、`nutrition_per_100` | 食物营养基准 |
| `recipes` | `name` | 菜品模板 |
| `recipe_ingredients` | `recipe_id`、`food_id`、`quantity` | 已归一化为该食物 g/ml 基准的食材用量 |
| `meal_entries` | `date`、`meal_type`、`item_type`、`food_id`、`recipe_id`、`quantity`、`snapshot`、`nutrition_totals` | 实际饮食及历史快照 |

具体约定：

- 三个目标百分比字段为 `protein_percent`、`carbohydrate_percent`、`fat_percent`。
- 查询某日目标：优先取 `daily_goals`，否则取 `effective_on <= date` 中最新的 `goal_settings`。
- 更新当天默认目标时写入或更新当天的生效记录，不改动更早记录。当天已有明确覆盖值时，覆盖值继续优先。
- 食材关联使用外键；替换一道菜的配方在同一事务内完成。
- `meal_entries.item_type` 为 `food` 或 `recipe`。食物记录只填写 `food_id` 和归一化数量；菜品记录只填写 `recipe_id`，数量为空。
- `meal_entries` 对日期和餐次建立索引，支撑每日查询。
- 创建饮食记录时，在事务内读取一致的配方和营养数据，生成并保存快照与合计。
- 每餐和每日汇总直接从饮食记录计算，V1 不额外建立汇总表或缓存。

## 5. HTTP API

接口统一以 `/api/v1` 开头，使用 JSON。列表接口返回 `items`，详情接口返回对象。食物和菜品支持 `q` 名称搜索及 `page`、`page_size` 分页，默认每页 20 条、最多 100 条。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET / PUT | `/goal-settings/default` | 查询或更新当前默认目标；首次查询可返回 `null` |
| GET / PUT / DELETE | `/daily-goals/{date}` | 查询该日最终目标、设置覆盖、删除覆盖；查询说明来源 `default` / `override` / `none` |
| GET / POST | `/foods` | 搜索列表、创建食物 |
| GET / PATCH | `/foods/{id}` | 食物详情、修改名称或营养数据 |
| GET / POST | `/recipes` | 搜索列表、创建菜品 |
| GET / PUT | `/recipes/{id}` | 查询含营养合计的详情、整体替换名称和食材列表 |
| GET / POST | `/meal-entries` | 按 `date` 和可选 `meal_type` 查询记录、创建记录 |
| GET / PATCH / DELETE | `/meal-entries/{id}` | 记录详情、修改、删除 |
| GET | `/daily-summary?date=YYYY-MM-DD` | 返回目标、三餐合计、全天合计和剩余额度 |

### 请求示例

设置默认目标：

```json
{
  "energy_kcal": 2000,
  "protein_percent": 30,
  "carbohydrate_percent": 40,
  "fat_percent": 30
}
```

创建菜品，以下 ID 仅为示例：

```json
{
  "name": "番茄炒蛋",
  "ingredients": [
    {"food_id": 1, "quantity": 400, "unit": "g"},
    {"food_id": 2, "quantity": 100, "unit": "g"},
    {"food_id": 3, "quantity": 50, "unit": "g"},
    {"food_id": 4, "quantity": 10, "unit": "g"}
  ]
}
```

分别调用记录接口，可以在同一餐混合记录饮品和菜品：

```json
{
  "date": "2026-09-08",
  "meal_type": "lunch",
  "item_type": "food",
  "food_id": 5,
  "quantity": 250,
  "unit": "ml"
}
```

```json
{
  "date": "2026-09-08",
  "meal_type": "lunch",
  "item_type": "recipe",
  "recipe_id": 1
}
```

### 响应与错误约定

- 创建成功返回 `201` 和对象；查询、更新返回 `200`；删除成功返回 `204`。
- PATCH 中未提供的字段保持原值；修改营养对象时逐字段更新，显式 `null` 表示将该营养改为未知。
- 汇总指标形如 `{"known_total": 30, "complete": false}`，表示已知部分合计为 30，仍有缺失数据。
- 日期、餐次、单位、数值、百分比及引用关系均由 Go 校验。
- 错误统一为 `{"error":{"code":"validation_error","message":"说明","fields":{}}}`；字段错误放在 `fields` 中。
- HTTP 状态码：格式错误 `400`、资源不存在 `404`、业务参数不合法 `422`、内部错误 `500`。
- OpenAPI 明确可空字段、营养单位、菜品整道计入的语义及汇总完整性；内部错误不向客户端暴露数据库细节。

## 6. 开发顺序与验收

### 第一步：Go 服务与数据库

初始化 Go 模块、Gin、配置、GORM、Goose、Docker Compose 和统一错误处理。提供健康检查与基础 OpenAPI 文档，验证空数据库可完成迁移。

### 第二步：目标、食物与营养计算

完成默认目标生效记录、按日覆盖、食物维护、单位换算和营养计算。

重点验证：百分比换算正确；修改默认目标不改变历史；日期覆盖优先；kg/L 正确归一化；不接受跨类型单位；未知与零保持区别。

### 第三步：菜品

完成固定配方维护和营养汇总。

重点验证：配方按食材用量计算；重量与体积食材可以共存；缺失营养正确传播；非法食材或用量使整个配方写入失败；查询反映食物最新数据。

### 第四步：饮食记录与每日汇总

完成混合记录、快照、补记、修改、删除及目标对比。

重点验证：整道菜完整计入；同餐混合食物和菜品；修改模板不改变历史；修改食物摄入量沿用原营养快照；缺失营养不产生虚假的剩余额度；修改和删除后汇总正确。

### 第五步：联调与交付

补齐 OpenAPI 请求、响应示例，使用少量测试食物跑通“设置目标 → 维护食物 → 创建菜品 → 记录三餐 → 查看汇总”。CI 执行单元测试和 PostgreSQL 集成测试；测试库与个人使用数据隔离。

V1 完成标准：仅通过 HTTP 接口即可完成上述流程，并能纠正记录、保留历史和准确表达缺失数据。

## 7. 后续 Agent 接入边界

- Python 使用 FastAPI + Pydantic + LangChain + LangGraph，通过 Go 接口操作业务数据。
- 图片或对话先转为结构化参数；食物匹配、单位和数量不明确时补问，营养计算始终由 Go 完成。
- 推荐中的单次配方调整不修改模板，也不自动计入实际饮食；记录该菜品时保存本次实际配方及营养快照。
- Agent 写入时补充请求去重机制，避免重试产生重复饮食记录。
- Agent 检查点与 Go 业务表分别管理；流式响应使用 SSE。定时任务、Redis + Asynq 和 OpenTelemetry 按后续学习阶段接入。
